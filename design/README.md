# Windkeel design

The design library for Windkeel's UI. How to *use* it — color roles, type, spacing, states, voice —
is in [`guidelines.md`](guidelines.md). This file covers how it's built.

## Using it

One stylesheet carries everything: fonts, tokens for both themes, and every component.

```html
<link rel="stylesheet" href="design/windkeel.css" />
<button class="oq-button oq-button--primary">Open pull request</button>
<span class="oq-badge" data-intent="success">2 passed</span>
```

Components are plain CSS classes (`oq-` prefix) on native HTML elements, so they work under any
framework; each component's `README.md` says exactly what markup it expects. Open
[`gallery.html`](gallery.html) from disk to see all of them in both themes, and
[`palette.html`](palette.html) for the color scales.

| Group | Components |
| --- | --- |
| Actions | Button, Kbd |
| Forms | TextField, Switch |
| Navigation | Tabs, SegmentedControl, NavItem |
| Status | Badge, StatusDot, Spinner |
| Feedback | Banner, Toast, Dialog |
| Layout | Card |
| Agent | Avatar, Message, AgentStep, Terminal, DiffView, Composer, EvidenceList |

## Layout of this folder

| Path | What | Edit? |
| --- | --- | --- |
| `guidelines.md` | Usage rules (the design system's README) | yes |
| `tokens/foundation.mjs` | Type, spacing, radius, shadow, size, z-index, motion | yes |
| `scripts/generate-colors.mjs` | Color parameters and contrast checks | yes |
| `components/base.css`, `components/intents.css` | Page defaults; the `data-intent` color mapping | yes |
| `components/<Name>/` | `*.css`, `README.md` (usage), `preview.html` (live example) | yes |
| `components/Cover/preview.html` | The design system's cover | yes |
| `tokens/color.css`, `tokens/color.json` | Generated by `generate-colors.mjs` | no |
| `tokens/foundation.css`, `windkeel.css`, `gallery.html` | Generated by `build.mjs` | no |

```sh
node design/scripts/generate-colors.mjs   # after changing colors
node design/scripts/build.mjs             # after changing anything else
```

Adding a component: make `components/<Name>/` with its CSS, a `README.md` (first sentence is the
summary; then what the consumer provides and the don'ts) and a `preview.html` whose first line is
`<!-- @dsCard group="<Group>" height=<px> subtitle="…" -->`. Use only `--color-*` and foundation
tokens, then run the build.

### The published design system

The same sources are published as a claude.ai Design System artifact, a browsable reference for
people and agents. `node design/scripts/build.mjs --export <dir>` writes its file tree to
`<dir>/project/`. The first publish sends everything. After that, send only the files that
changed, and keep the artifact's existing `design-system.json`.

## Color

### The idea

An agent UI has two actors — you and the agent — and a lot of state. The palette gives each its
own lane so they never compete:

- **Graphite** (neutral, faint blue cast) is the shell: surfaces, borders, text. Most of the
  screen.
- **Iris** is *you*: anything you can act on — primary buttons, links, selection, focus.
- **Cyan** is *the agent*: anything it is doing right now — thinking, running a tool,
  streaming. When cyan disappears from the screen, the agent is idle.
- **Green / amber / red / blue** are status only: success, warning, danger, info. They map
  directly onto an evidence package's verdicts (pass, warn, fail) and are never used for
  decoration.

The accent is kept away from all four status hues, so "clickable" and "result" are never
confused.

When a person works in a workspace of their own (ADR-0029, proposed), their work gets no hue: it is
drawn with their avatar and name in graphite text, and commits say *you*, *Windkeel* or *mixed*. Cyan
stays the agent's alone, so it still disappearing means the agent is idle, even while you type.

### Two layers

**Scales** — seven hues × 12 steps (`--iris-1` … `--iris-12`). Each step has a fixed job:

| Step | Job | Step | Job |
| --- | --- | --- | --- |
| 1 | app background | 7 | border |
| 2 | subtle background | 8 | strong border |
| 3 | element background | 9 | solid fill |
| 4 | element hovered | 10 | solid fill, hovered |
| 5 | active / selected | 11 | low-contrast text |
| 6 | subtle border | 12 | high-contrast text |

Lightness is shared across hues within a theme, so `blue-3` and `red-3` sit at the same visual
weight.

**Semantic tokens** — `--color-*`. These are what components use. Each points at a scale step,
and the step it points at changes per theme, so one component is correct in light and dark.

| Group | Tokens |
| --- | --- |
| Surface | `bg-canvas`, `bg-surface`, `bg-raised`, `bg-sunken` (code, terminal, logs), `bg-overlay`, `bg-hover`, `bg-active`, `bg-inverse`, `bg-scrim` |
| Border | `border-subtle`, `border-default`, `border-strong` |
| Text | `text-primary`, `text-secondary`, `text-tertiary`, `text-disabled`, `text-inverse`, `text-link` |
| Accent | `accent-solid`, `accent-solid-hover`, `accent-on-solid`, `accent-subtle`, `accent-subtle-hover`, `accent-border`, `accent-text`, `focus-ring`, `selection` |
| Agent, success, warning, danger, info | `<intent>-solid`, `-solid-hover`, `-on-solid`, `-subtle`, `-border`, `-text` |
| Verdict | `verdict-pass`, `verdict-fail`, `verdict-warn`, `verdict-skipped`, `verdict-running` |
| Diff | `diff-add-bg`, `diff-add-emphasis`, `diff-add-text`, and the same for `diff-remove-*` |

Rule of thumb: if a component reaches for `--red-11` instead of `--color-danger-text`, a semantic
token is missing — add it rather than bypass the layer.

### Using it

```html
<link rel="stylesheet" href="design/tokens/color.css" />
```

```css
.button-primary {
  background: var(--color-accent-solid);
  color: var(--color-accent-on-solid);
}
.button-primary:hover { background: var(--color-accent-solid-hover); }
```

The theme follows the OS. Force one with `<html data-theme="light">` or `data-theme="dark"`.

`tokens/color.json` holds the same values in the [W3C Design Tokens](https://design-tokens.github.io/community-group/format/)
format, for Tailwind, Figma or native targets.

### Changing it

Both token files are generated. Edit the parameters at the top of
`scripts/generate-colors.mjs` (OKLCH lightness ladder, chroma curve, and one solid color per
hue), then:

```sh
node design/scripts/generate-colors.mjs          # regenerate
node design/scripts/generate-colors.mjs --check  # contrast checks only
```

The script refuses to write if any pairing drops below its WCAG minimum: body text 7:1 on
surfaces, secondary text and every status text 4.5:1, text on every solid (and its hover)
4.5:1, focus ring and solids 3:1 against the page — in both themes.
